Getting started
What exactly is "the backend"?

Everything that runs on computers you don't see: the servers that receive requests, the code that enforces rules ("is this password right?", "is this seat still free?"), and the databases that remember it all. The frontend is the restaurant's dining room; the backend is the kitchen, the pantry and the ordering system. FIG. 01 on the home page shows one order moving through that kitchen.

Which language should I learn first for backend?

Pick one and stop worrying — the concepts on this site transfer to all of them. Sensible first picks: JavaScript/Node.js (one language for front and back), Python (gentlest syntax, huge ecosystem), or Go (simple, fast, built for servers). Java and C# dominate large companies.

The trap is switching languages every month. HTTP, databases, caching and queues are the career; the language is just the accent you speak them in.

Do I need to be good at math?

No. You need logic and patience, not calculus. The closest thing to math you'll use daily is Big-O reasoning (FIG. 10) — which is really just "will this get slow when the data grows?" — and back-of-envelope estimates like "1M requests/day ≈ 12/second".

Frontend first or backend first?

Either works; people succeed both ways. Backend-first suits you if you like logic, data and systems more than visuals. You can build and test entire backends with just a terminal and tools like curl or Postman — no CSS required. (This site is, ironically, a frontend. We appreciate the irony.)

Concepts
What's the difference between an API and a backend?

The backend is the whole kitchen; the API is the serving window. An API (Application Programming Interface) is the defined set of URLs, methods and formats through which the outside world may talk to your backend — like GET /users/42 in FIG. 02. Backend = implementation, API = contract.

REST vs GraphQL — which one should I learn?

REST first, always. It's simpler, it's the majority of real-world APIs, and it teaches HTTP properly. GraphQL solves a specific problem — clients needing flexible queries without dozens of endpoints — and it's much easier to appreciate after you've felt that pain in REST.

SQL or NoSQL — which database do I start with?

SQL (PostgreSQL is the default choice). Relational databases + SQL are the single most transferable backend skill: 50 years old and still running banks, hospitals and startups. NoSQL stores (MongoDB, Redis, DynamoDB) are specialized tools you add when a specific problem calls for them — Redis, for instance, is essentially FIG. 05 and FIG. 11 as a product.

What is "state", and why does everyone say HTTP is stateless?

State is anything the system remembers. HTTP itself remembers nothing between requests — each one arrives as a stranger. So backends bolt memory on: cookies and sessions (server remembers you) or JWTs (you carry the proof yourself — FIG. 08). "Stateless services" are prized because any server can handle any request, which is what makes FIG. 06's load balancing trivially easy.

What actually happens when I type a URL and press Enter?

The favorite interview question of all time. Short version: DNS turns the name into an IP → TCP + TLS open a secure pipe → your browser sends an HTTP request → a load balancer picks a server → the server checks auth, cache, then the database → a response streams back and renders. Long version: press ▶ on FIG. 01 and read the log lines.

DSA & interviews
How much DSA do I really need for backend work?

For building: the five ideas on the DSA page — hash tables, trees, stacks, queues, Big-O — because they're inside every tool you'll use. For interviews at big tech: more grinding is sadly real (arrays, strings, two pointers, BFS/DFS, dynamic programming basics). But learn the five first; they make the grind meaningful instead of ritualistic.

What is a "system design interview" and when do I care?

It's being asked to draw FIG. 01 for a real product: "design Instagram's feed" or "design a URL shortener". You sketch load balancers, caches, queues, databases and their trade-offs — literally the modules of this site composed together. Junior roles rarely require it; it becomes the main event for senior roles. Every figure here is a future whiteboard box.

Practice & shipping
What should I build first?

The classic ladder, each rung adding one new concept:

1) A to-do API — CRUD, routes, JSON. 2) Add a database — persistence, migrations. 3) Add auth — registration, login, JWTs. 4) A URL shortener — redirects, an index, your first cache. 5) A chat or notification service — queues and websockets. By rung 5 you've personally implemented FIGS. 02–08.

How do I put a backend on the internet without spending money?

Free tiers cover your whole learning phase: Render, Railway or Fly.io for the app; Neon or Supabase for a Postgres database; Upstash for Redis. (Static sites like this one ride free forever on GitHub Pages.) The skill of deploying — env vars, logs, "works on my machine" archaeology — teaches as much as the code does.

How long until I'm employable?

Honest range: 6–18 months of consistent building (not consistent video-watching). The portfolio that gets interviews is 2–3 deployed projects with README files that explain the decisions — "I added a queue because emails blocked signup" is worth more than any certificate.

They're honest miniatures.
