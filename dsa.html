Only the DSA you'll actually use

You don't need 300 LeetCode problems to build backends. You need five ideas — because each one is silently running inside every database, cache and web framework you'll ever touch.

DSA 01

Big-O: the cost forecast

Big-O answers one question: when my data grows, how fast does my work grow? It ignores constants and asks only about the shape of the curve.

Backend translation: O(1) is a cache/hash lookup, O(log n) is an index seek, O(n) is a full table scan, O(n²) is the nested loop that works in the demo and melts in production.

Try: drag from 10 to 1,000,000 rows. O(1) and O(log n) barely flinch. O(n²) exits the known universe.

at 1 op/µs, O(n²) here takes ~17 min
🔧 Go deeper — how Big-O shows up in real code

You rarely compute Big-O on paper. You choose a data structure, and its Big-O comes along. The trap below is the most common accidental O(n²) in backend code.

// Task: for each order, attach its user. Two ways, wildly different cost.

// ❌ O(n × m) — .find scans the whole users array for EVERY order.
// 10k orders × 10k users = 100,000,000 comparisons. Melts in prod.
const slow = orders.map(o =>
  ({ ...o, user: users.find(u => u.id === o.userId) })
);

// ✅ O(n + m) — build a hash index once, then O(1) lookups.
const byId = new Map(users.map(u => [u.id, u]));   // one pass
const fast = orders.map(o =>
  ({ ...o, user: byId.get(o.userId) })             // O(1) each
);

// Same idea inside the DB: a JOIN on an indexed column is the fast path;
// a JOIN with no index is the slow, nested-loop version.
// ❌ O(n × m): linear search per order
for _, o := range orders {
	for _, u := range users { // scans every user, every time
		if u.ID == o.UserID {
			o.User = u
			break
		}
	}
}

// ✅ O(n + m): index into a map first, then O(1) lookups
byID := make(map[string]User, len(users))
for _, u := range users {
	byID[u.ID] = u // one pass to build
}
for i := range orders {
	orders[i].User = byID[orders[i].UserID] // O(1)
}

Going further

The whole skill is spotting a loop-inside-a-loop over data and replacing the inner loop with a map lookup. Backend translation: the same pattern is a database JOIN on an indexed column vs an un-indexed one. When in doubt, measure — console.time() in Node, testing.B benchmarks in Go — and try it at 10× the data you expect.
DSA 02

Hash tables: the O(1) machine

Take a key, run it through a hash function, get a bucket number, go straight there. No searching — computing the location. This one trick powers dictionaries, Redis, session stores, DB hash indexes and your cache from FIG. 05.

Two keys can land in the same bucket — a collision. The standard fix is chaining: each bucket holds a small list. As buckets fill up, real implementations resize and re-hash everything.

Try: insert cart and user-like keys until two collide, then look one up and watch it walk the chain.
FIG. 118-bucket hash table · chaining hash(key) % 8 → bucket
🔧 Go deeper — hash maps you'll use every day

You almost never implement a hash table — the language gives you one. But knowing it's O(1) tells you when to reach for it: de-duping, counting, grouping, caching, lookups.

// The built-in hash tables: Map (any key) and plain objects (string keys)
const cache = new Map();
cache.set("user:42", { name: "Ada" });  // O(1) insert
cache.get("user:42");                    // O(1) lookup
cache.has("user:42");                    // O(1)
cache.delete("user:42");                 // O(1)

// Count occurrences — O(n) total, O(1) per item
const counts = new Map();
for (const tag of tags)
  counts.set(tag, (counts.get(tag) ?? 0) + 1);

// De-duplicate a list in O(n) using a Set (a keys-only hash table)
const unique = [...new Set(ids)];

// Group orders by user — the "index" pattern from the Big-O section
const byUser = new Map();
for (const o of orders)
  (byUser.get(o.userId) ?? byUser.set(o.userId, []).get(o.userId)).push(o);
// Go's built-in map is a hash table
cache := make(map[string]User)
cache["user:42"] = User{Name: "Ada"} // O(1) insert
u, ok := cache["user:42"]             // O(1) lookup; ok = was it present?
delete(cache, "user:42")             // O(1)

// Count occurrences
counts := make(map[string]int)
for _, tag := range tags {
	counts[tag]++ // missing keys read as zero — no init needed
}

// De-duplicate using a set (map to empty struct = zero memory per value)
seen := make(map[string]struct{})
var unique []string
for _, id := range ids {
	if _, dup := seen[id]; !dup {
		seen[id] = struct{}{}
		unique = append(unique, id)
	}
}

Going further

Redis is "a hash table as a network service" — the cache and rate-limiter modules are this structure, shared across all your servers. Caveats: map iteration order is not guaranteed (Go randomizes it on purpose); a plain Go map is not safe for concurrent writes — use sync.Map or a mutex. Hash lookups are O(1) on average; a pathological set of colliding keys degrades to O(n), which is why real implementations resize.
DSA 03

Stacks & queues: order is everything

Same data, opposite discipline. A stack is LIFO — last in, first out: it's literally how your language runs function calls. A queue is FIFO — first in, first out: it's the job queue from FIG. 07 and every "fair" waiting line in computing.

FIG. 12BQueue · FIFO · the job line
oldest job leaves first — nobody cuts the line
🔧 Go deeper — stacks & queues in practice

Both are one-liners on top of a dynamic array. You'll use a stack for undo/parsing/traversal, and a queue for job processing and breadth-first walks.

// STACK (LIFO) — just an array with push/pop, both O(1)
const stack = [];
stack.push("a"); stack.push("b");
stack.pop();            // "b" — last in, first out

// Real use: validate balanced brackets in a config/expression
function balanced(s) {
  const st = [], pairs = { ")": "(", "]": "[", "}": "{" };
  for (const ch of s) {
    if ("([{".includes(ch)) st.push(ch);
    else if (ch in pairs && st.pop() !== pairs[ch]) return false;
  }
  return st.length === 0;
}

// QUEUE (FIFO). Beware: array.shift() is O(n) — it re-indexes everything.
// For a real queue use a linked structure or two-stack trick.
// Node's job queues (BullMQ) do this for you over Redis.
class Queue {                 // O(1) enqueue AND dequeue
  in = []; out = [];
  enqueue(x) { this.in.push(x); }
  dequeue() { if (!this.out.length) while (this.in.length) this.out.push(this.in.pop()); return this.out.pop(); }
}
// STACK — a slice; append to push, reslice to pop. Both O(1) amortized.
stack := []string{}
stack = append(stack, "a")          // push
top := stack[len(stack)-1]          // peek
stack = stack[:len(stack)-1]        // pop

// QUEUE — for a robust O(1) FIFO, container/list (a doubly linked list)
import "container/list"

q := list.New()
q.PushBack("job-1")                 // enqueue at the back
q.PushBack("job-2")
front := q.Front()                  // oldest
q.Remove(front)                     // dequeue — O(1)

// In a real service the "queue" is a buffered channel or Redis;
// this call stack (LIFO) is literally how Go runs your functions.

Going further

The call stack is a stack you use without noticing — infinite recursion overflows it (the site's namesake). The job queue is the message queue from Backend Core. Gotcha: JavaScript's Array.shift() and naively re-slicing the front of a Go slice are O(n); the two-stack trick (Node) or container/list (Go) keep dequeue O(1) when it matters.
DSA 04

Search trees: how indexes find anything

Keep keys sorted in a tree: smaller to the left, bigger to the right. Now any search is a series of yes/no questions — each one throws away half the data. A million keys? Found in ~20 hops. That's the O(log n) from the index race in FIG. 04.

Real databases use B-trees — the same idea, but each node holds many keys so it fits a disk page and the tree stays only 3–4 levels deep, even with billions of rows.

Try: insert 10 random keys, then search for one. Count the hops — then imagine the tree with a million keys. Still ~20 hops.

🔧 Go deeper — trees are the DB index; use sorted structures

You almost never hand-roll a balanced tree — the database's B-tree index is the tree that matters, and it's created with one line of SQL. When you need sorted, in-memory ordering, reach for a library or keep a sorted slice.

-- The tree you actually use: a B-tree index. One line.
CREATE INDEX idx_events_created ON events(created_at);

-- Now range + sorted queries are O(log n) seeks, not O(n) scans:
SELECT * FROM events WHERE created_at > now() - interval '1 day'
ORDER BY created_at DESC LIMIT 100;

// In JS, the built-in "sorted structure" is just a sorted array +
// binary search — O(log n) to find, O(n) to insert (shifting).
function bsearch(sortedArr, target) {
  let lo = 0, hi = sortedArr.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;          // same halving the BST does
    if (sortedArr[mid] === target) return mid;
    if (sortedArr[mid] < target) lo = mid + 1; else hi = mid - 1;
  }
  return -1;
}
// Need a real balanced tree in memory? Use a library (e.g. sorted-btree).
// The tree that matters is the DB index:
//   CREATE INDEX idx_events_created ON events(created_at);

// In Go, sort.Search is binary search over a sorted slice — O(log n):
import "sort"

nums := []int{3, 12, 25, 37, 50, 62, 88} // must be sorted
i := sort.Search(len(nums), func(i int) bool { return nums[i] >= 37 })
if i < len(nums) && nums[i] == 37 {
	// found at index i in ~log2(n) steps
}

// For an ordered map/tree in memory, use a library such as
// github.com/google/btree — but 99% of the time, let Postgres'
// B-tree index do the sorted lookups for you.

Going further

A database B-tree keeps billions of rows only 3–4 levels deep, so any lookup is a handful of disk reads. That's why WHERE indexed_col = ? and ORDER BY indexed_col are fast and un-indexed ones aren't. The binary search above is the same halving idea a search tree performs at every node — understand one and you understand both.
DSA 05

Arrays vs linked lists

An array is one contiguous block: element #7 lives at start + 7 × size, so jumping to any index is instant. A linked list scatters nodes across memory, each pointing to the next: to reach #7 you must walk through six others.

Backend relevance: rows in a table page, items in a Redis list, buffers in your web server — access patterns decide which wins. Arrays for random reads, lists for cheap inserts at the ends.

Try: access index 7 in both. One step vs eight. Then insert at the front — and watch the array pay for its neat layout by shifting everything.

🔧 Go deeper — arrays vs lists, and why it's usually arrays

The figure showed the trade-off. In practice you reach for the dynamic array (JS Array, Go slice) almost every time — CPUs love contiguous memory. Linked lists earn their place only for cheap end-inserts and O(1) splicing.

// ARRAY — random access O(1), insert-at-front O(n) (shifts everything)
const arr = [10, 20, 30];
arr[2];              // O(1) — jump straight to the address
arr.push(40);        // O(1) amortized — append at the end
arr.unshift(5);      // O(n) — every element shifts right
arr.splice(1, 0, 15);// O(n) — insert in the middle

// LINKED LIST — insert/remove at a known node O(1), but access is O(n)
class Node { constructor(v) { this.v = v; this.next = null; } }
// You rarely build this by hand in JS; the array is faster in practice
// because contiguous memory is cache-friendly. Prefer arrays unless you
// profile and prove otherwise.
// SLICE — the workhorse. Contiguous, cache-friendly, index O(1).
s := []int{10, 20, 30}
_ = s[2]                       // O(1) random access
s = append(s, 40)             // O(1) amortized append
s = append([]int{5}, s...)    // O(n) prepend — copies everything

// LINKED LIST — standard library, when you need O(1) middle splices
import "container/list"
l := list.New()
e := l.PushBack(20)
l.InsertBefore(10, e)         // O(1) given the element pointer
l.Remove(e)                   // O(1)

// Rule of thumb: default to a slice. Contiguous memory beats pointer-
// chasing so often that "just use a slice/array" is usually right.

Going further

Modern CPUs read memory in cache lines, so walking a contiguous array is dramatically faster than chasing a linked list's scattered pointers — even when Big-O says they're equal. This is why "the array is fine" is usually the correct backend answer. Rows in a table page, items in a Redis list, and bytes in your HTTP buffer are all contiguous for exactly this reason.
