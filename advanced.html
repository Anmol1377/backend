MODULE 09

SSL/TLS: the padlock handshake

The S in HTTPS. Before any data flows, client and server perform a TLS handshake: the server proves its identity with a certificate signed by a trusted authority, then both sides agree on a shared secret key. After that, everything is symmetrically encrypted.

("SSL" is the retired 1990s name; the modern protocol is TLS 1.2/1.3 — but the old name stuck to the padlock.) TLS gives you three things: encryption (nobody reads it), integrity (nobody alters it), authentication (you're talking to the real server).

Try: step through the handshake, then hit EAVESDROP at each step to see exactly what an attacker on the wifi can and can't read.

🔧 Go deeper — actually serve HTTPS

You rarely implement TLS — you enable it. In production a reverse proxy terminates it; here's how each runtime does it directly, plus the tool that gets you a free, auto-renewing certificate.

import https from "node:https";
import fs from "node:fs";

// You need a cert + private key. In dev, generate a self-signed pair:
//   openssl req -x509 -newkey rsa:2048 -nodes -keyout key.pem \
//     -out cert.pem -days 365
const options = {
  key: fs.readFileSync("key.pem"),
  cert: fs.readFileSync("cert.pem"),
};

https.createServer(options, app).listen(443);

// In real life you DON'T do this — you put nginx/Caddy/a cloud LB in
// front to terminate TLS and auto-manage certs. Node speaks plain HTTP
// on an internal port; the proxy handles the padlock (see FIG. 21).
package main

import "net/http"

func main() {
	// Serve HTTPS from a cert + key pair:
	http.HandleFunc("/", handler)
	http.ListenAndServeTLS(":443", "cert.pem", "key.pem", nil)
}

Going further

Get free, auto-renewing certificates from Let's Encrypt — or better, let Caddy or your cloud load balancer do it with zero config. Redirect all HTTP to HTTPS and send an HSTS header so browsers refuse plaintext. Never ship a self-signed cert to production (browsers show a scary warning) — it's for local dev only. Modern default: TLS 1.3.
MODULE 10

CORS: the browser's border control

By default, a browser refuses to let JavaScript on site-a.com read responses from site-b.com — the same-origin policy. CORS is how a server opts in: it answers with Access-Control-Allow-Origin headers naming who may read its responses.

The error every developer meets on day one — "blocked by CORS policy" — is the browser protecting users, not the server rejecting you. In fact the server often already processed the request; the browser just refuses to hand the response to the page's JavaScript.

Try: fetch as localhost:3000 against a server that only allows the production origin — the classic local-dev wall. Then fix it server-side.

🔧 Go deeper — configure CORS correctly (and safely)

CORS is a few lines of server config. The danger is getting lazy and allowing * on an authenticated API — which lets any website read your users' data.

// npm i cors
import cors from "cors";

// ✅ Allow only the origins you trust, and only if you send cookies/creds
app.use(cors({
  origin: ["https://app.example.com", "http://localhost:3000"], // dev too
  methods: ["GET", "POST", "PUT", "DELETE"],
  credentials: true,          // needed if the browser sends cookies
}));

// ❌ DON'T do this on an API that returns private/user data:
// app.use(cors({ origin: "*" }));   // any site on the internet can read it
// (Also: "*" is forbidden together with credentials:true — by design.)

// The browser sends a preflight OPTIONS request for non-simple calls;
// the cors middleware answers it automatically.
// go get github.com/rs/cors
import "github.com/rs/cors"

c := cors.New(cors.Options{
	AllowedOrigins: []string{
		"https://app.example.com",
		"http://localhost:3000", // your dev frontend
	},
	AllowedMethods:   []string{"GET", "POST", "PUT", "DELETE"},
	AllowCredentials: true,
})

handler := c.Handler(mux) // wrap your router
http.ListenAndServe(":3000", handler)

// Same rule: never pair AllowedOrigins:["*"] with AllowCredentials:true.
// Echo only origins you actually trust.

Going further

Remember who enforces CORS: the browser. Server-to-server calls and tools like curl ignore it entirely — so CORS is not a security boundary, it's a browser convenience/guardrail. Real access control is auth + the RBAC/ABAC module. The "* is fine, it's public data" call is only safe when the data really is public and unauthenticated.
MODULE 11

Rate limiting: the token bucket

Every public API gets abused — scrapers, brute-forcers, runaway loops. A rate limiter gives each client a budget. The classic algorithm is the token bucket: the bucket holds N tokens, refills at a steady rate, and every request spends one. Empty bucket → 429 Too Many Requests.

The elegance: steady users never notice, while bursts get absorbed up to the bucket size and floods get rejected cheaply. Real implementations keep one bucket per API key or IP — in Redis, naturally.

Try: send single requests (fine), then BURST 15 and watch the last five bounce with 429s. Lower the refill rate to make the limiter stricter.

🔧 Go deeper — a distributed rate limiter with Redis

A per-process counter breaks the moment you run two servers (each allows the full quota). Real limiters keep the bucket in Redis so all servers share one count per client.

// Simple & solid: express-rate-limit backed by Redis
// npm i express-rate-limit rate-limit-redis ioredis
import rateLimit from "express-rate-limit";
import { RedisStore } from "rate-limit-redis";
import Redis from "ioredis";
const redis = new Redis(process.env.REDIS_URL);

const limiter = rateLimit({
  store: new RedisStore({ sendCommand: (...a) => redis.call(...a) }),
  windowMs: 60_000,     // per minute
  limit: 100,           // 100 requests per key per window
  keyGenerator: (req) => req.user?.id ?? req.ip, // per user, else per IP
  standardHeaders: true,// sends RateLimit-* headers
  handler: (req, res) => res.status(429).json({ error: "slow down" }),
});

app.use("/api/", limiter); // protect the whole API
// Token bucket per client, shared via Redis (atomic INCR + TTL).
// Libraries: github.com/ulule/limiter or go-redis/redis_rate.
import "github.com/go-redis/redis_rate/v10"

limiter := redis_rate.NewLimiter(rdb)

func rateLimit(next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		key := clientKey(r) // user id or IP
		// allow 100 requests per minute, refilled steadily
		res, _ := limiter.Allow(r.Context(), key, redis_rate.PerMinute(100))
		if res.Allowed == 0 {
			w.Header().Set("Retry-After", "1")
			http.Error(w, "slow down", http.StatusTooManyRequests) // 429
			return
		}
		next(w, r)
	}
}

Going further

Rate-limit by identity (API key or user id), falling back to IP for anonymous traffic. Return 429 with a Retry-After header so well-behaved clients back off. Put the limiter at the edge (nginx, API gateway, Cloudflare) for cheap, early rejection, and keep an app-level limiter for per-user fairness. Common algorithms: token bucket (shown) and sliding-window counter.
MODULE 12

SQL injection — and its one true fix

If you build SQL by gluing user input into a string, the user can finish your sentence for you. The payload ' OR '1'='1 turns "find this user" into "find every user". This single bug has leaked more databases than any other.

The fix is not cleverness — it's parameterized queries (prepared statements). The query shape and the data travel separately, so input is always treated as a value, never as SQL. Every ORM and driver does this; you just have to not bypass it.

Try: inject the payload in concatenation mode and breach the table. Flip to parameterized and watch the same payload become a harmless, weird username.

🔧 Go deeper — the vulnerable line vs the safe line

This is the single most important pair of snippets on the whole site. Learn to recognize the top one on sight and never write it.

// ❌ VULNERABLE — user input becomes part of the SQL text.
// Input:  ' OR '1'='1' --   →  returns every row / logs in as anyone.
const q = `SELECT * FROM users WHERE name = '${name}'`;
await pool.query(q);                      // NEVER do this

// ✅ SAFE — parameterized. The driver sends the SQL and the value
// separately, so input is ALWAYS data, never executable SQL.
await pool.query(
  "SELECT * FROM users WHERE name = $1",
  [name]                                  // the fix. That's it.
);

// ORMs do this for you — but you can still bypass them:
await prisma.user.findMany({ where: { name } });        // safe
await prisma.$queryRawUnsafe(`... ${name} ...`);        // ❌ unsafe again

// Same rule guards against XSS on the output side: never inject
// untrusted input into HTML/queries/commands without escaping.
// ❌ VULNERABLE — building SQL with fmt.Sprintf
q := fmt.Sprintf("SELECT * FROM users WHERE name = '%s'", name)
db.Query(q) // one ' in `name` and an attacker owns your database

// ✅ SAFE — placeholders. database/sql never interpolates the value.
db.QueryRow("SELECT * FROM users WHERE name = $1", name).Scan(&u.ID)

// sqlc / GORM generate parameterized queries for you:
//   db.Where("name = ?", name).First(&u)   // safe
// Just don't hand-concatenate. Ever.

Going further

Parameterization is the fix — not blocklists, not stripping quotes (attackers always find an encoding you missed). Apply least privilege to the DB user so a breach can't DROP TABLE. The same "treat input as data, not code" rule defeats XSS (escape on HTML output) and command injection (never build shell strings from input — pass args as an array). Validate inputs, but never rely on validation for injection safety.
MODULE 13

RBAC & ABAC: who may do what

Authentication says who you are (FIG. 08); authorization says what you may do. RBAC (role-based) is a lookup table: roles × actions. Simple, auditable, and enough for most apps.

ABAC (attribute-based) evaluates a policy over attributes of the user, the resource and the context — "editors may edit their own documents during business hours". More expressive, harder to audit. Most real systems are RBAC with a few ABAC-style conditions bolted on.

Try: in RBAC, an editor can edit any document — spot the flaw. Switch to ABAC and make the same editor fail on a document they don't own.

🔧 Go deeper — RBAC middleware & an ABAC ownership check

Authorization is middleware plus, for ABAC, a check against the specific resource. Note how the ownership check has to load the row first — that's the essence of attribute-based access.

// RBAC — a middleware factory. req.user was set by the JWT middleware.
const require = (...roles) => (req, res, next) =>
  roles.includes(req.user.role)
    ? next()
    : res.status(403).json({ error: "forbidden" });

app.delete("/users/:id", require("admin"), deleteUser);        // role gate
app.get("/reports", require("admin", "analyst"), getReports);

// ABAC — the rule depends on the resource, so we must load it first.
async function editDoc(req, res) {
  const doc = await db.getDoc(req.params.id);
  const allowed =
    req.user.role === "admin" ||
    (req.user.role === "editor" && doc.ownerId === req.user.sub); // owns it?
  if (!allowed) return res.status(403).json({ error: "not yours" });
  await db.updateDoc(doc.id, req.body);
  res.json({ ok: true });
}
// RBAC — middleware that checks the role claim
func requireRole(roles ...string) func(http.HandlerFunc) http.HandlerFunc {
	return func(next http.HandlerFunc) http.HandlerFunc {
		return func(w http.ResponseWriter, r *http.Request) {
			u := userFromCtx(r)
			for _, role := range roles {
				if u.Role == role {
					next(w, r)
					return
				}
			}
			http.Error(w, "forbidden", http.StatusForbidden) // 403
		}
	}
}

// ABAC — decision uses attributes of user AND the specific resource
func editDoc(w http.ResponseWriter, r *http.Request) {
	u := userFromCtx(r)
	doc, _ := db.GetDoc(r.PathValue("id"))
	allowed := u.Role == "admin" || (u.Role == "editor" && doc.OwnerID == u.ID)
	if !allowed {
		http.Error(w, "not yours", http.StatusForbidden)
		return
	}
	db.UpdateDoc(doc.ID, readBody(r))
}

Going further

Check on the server, every time — never trust the frontend to hide a button. Start with RBAC (simple, auditable); add ABAC-style conditions (owns-it, same-tenant, business-hours) only where you need them. For complex policies, dedicated engines like OPA/Rego, Casbin, or Oso externalize the rules so they're testable and centralized.
MODULE 14

WebSockets: when the server speaks first

HTTP is request→response: the server can never start a conversation. For chat, live dashboards and games that's backwards. The old workaround is polling — asking "anything new?" every few seconds, mostly hearing "no".

A WebSocket starts as an HTTP request that upgrades into a persistent, two-way pipe. After one handshake, either side can send at any moment — millisecond delivery, no wasted requests. The cost: the server now holds an open connection per user, which is state to manage (remember FIG. 06).

Try: start both, then fire a few server events. Compare wasted requests and delivery delay — then imagine the polling column at 100,000 users.

🔧 Go deeper — a real-time server on both sides

A chat/notifications server in ~15 lines each. The client upgrades once; after that the server pushes whenever it wants — the polling column of the figure disappears.

// npm i ws
import { WebSocketServer } from "ws";
const wss = new WebSocketServer({ port: 8080 });
const clients = new Set();

wss.on("connection", (socket) => {
  clients.add(socket);                       // remember this connection
  socket.on("message", (data) => {
    // broadcast a chat message to everyone
    for (const c of clients) c.send(data.toString());
  });
  socket.on("close", () => clients.delete(socket)); // clean up!
});

// The SERVER can push at any time — no request needed:
function notify(userSocket, event) {
  userSocket.send(JSON.stringify(event));    // ~5ms, zero polling
}

// Browser side:
//   const ws = new WebSocket("wss://api.example.com/chat");
//   ws.onmessage = (e) => render(JSON.parse(e.data));
// go get github.com/gorilla/websocket
var upgrader = websocket.Upgrader{}

func chat(w http.ResponseWriter, r *http.Request) {
	conn, err := upgrader.Upgrade(w, r, nil) // HTTP -> WebSocket (101)
	if err != nil {
		return
	}
	defer conn.Close()

	for { // loop: read a message, echo/broadcast it
		mt, msg, err := conn.ReadMessage()
		if err != nil {
			break // client disconnected — exit and clean up
		}
		conn.WriteMessage(mt, msg) // the server can also write unprompted
	}
}

// Register: http.HandleFunc("/chat", chat)
// Each connection is one goroutine — cheap, but it IS held-open state.

Going further

Open connections are state — with multiple servers (FIG. 06), user A on server 1 and user B on server 2 can't see each other unless you fan messages through Redis pub/sub or a broker. Always handle disconnects and add heartbeats/ping-pong to detect dead sockets. If you only need server→client (live feeds, progress), Server-Sent Events (SSE) are simpler. Authenticate the upgrade request just like any other route.
MODULE 15

Reverse proxy: the front desk

A reverse proxy (nginx, Caddy, Traefik) is the one server the internet actually talks to. It terminates TLS (FIG. 15), then routes each path to the right internal service — your app on port 3000, static files from disk, an admin panel kept off the public net.

Along the way it compresses responses, caches static assets, adds security headers and hides your internal topology. A load balancer (FIG. 06) is really just a reverse proxy with multiple targets per route.

Try: route all three requests. Notice the app server never handles images — and the outside world never learns that port 3000 exists.

🔧 Go deeper — a production nginx config

The figure's routing table is one real file. This is a lightly-trimmed but production-shaped nginx.conf that terminates TLS, serves static files, and proxies the rest to your app.

# /etc/nginx/nginx.conf — the one server the internet talks to
server {
  listen 443 ssl http2;
  server_name api.example.com;

  # 1. terminate TLS here (FIG. 15) — the app never sees certs
  ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
  ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

  # 2. serve static assets straight from disk, cached hard
  location /img/ {
    root /var/www/static;
    expires 1y;
    add_header Cache-Control "public, immutable";
  }

  # 3. lock the admin panel to the office network
  location /admin/ { allow 10.0.0.0/8; deny all; proxy_pass http://127.0.0.1:3000; }

  # 4. everything else -> the app (or an upstream {} pool = load balancing)
  location / {
    proxy_pass http://127.0.0.1:3000;   # app on a private port
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header Host $host;
  }
}
# redirect plain HTTP to HTTPS
server { listen 80; server_name api.example.com; return 301 https://$host$request_uri; }
# Caddyfile — Caddy fetches & auto-renews Let's Encrypt certs for you.
# This whole file replaces the nginx config on the left.
api.example.com {
    # automatic HTTPS — no cert paths, no cron renewals

    handle_path /img/* {
        root * /var/www/static
        file_server
        header Cache-Control "public, max-age=31536000, immutable"
    }

    @admin path /admin/*
    handle @admin {
        @office remote_ip 10.0.0.0/8
        handle @office { reverse_proxy 127.0.0.1:3000 }
        respond 403
    }

    reverse_proxy 127.0.0.1:3000   # everything else -> the app
}

Going further

A reverse proxy also does gzip/brotli compression, adds security headers (HSTS, X-Frame-Options), buffers slow clients, and hides your internal topology. List several backends in an nginx upstream {} block and it becomes a load balancer (FIG. 06). Caddy trades some flexibility for automatic HTTPS and a far shorter config — a great default for new projects.
MODULE 16

Docker: ship the machine, not the code

"Works on my machine" dies here. A Dockerfile describes an environment — OS, runtime, dependencies, your code — and builds it into an image: a stack of read-only layers. A container is that image running, isolated, identical on your laptop, CI, and every server.

Because containers start in seconds and are disposable, they're the unit everything else operates on: the load balancer's targets (FIG. 06), the workers behind your queue (FIG. 07), the things Kubernetes herds.

Try: build the image layer by layer, then run three containers from it. Same image, same behavior — that's the entire pitch.

🔧 Go deeper — real Dockerfiles & docker-compose

The layers in the figure come from a Dockerfile. These are multi-stage builds — the pattern that keeps images small and fast — for each runtime, plus the compose file that runs your app, Postgres and Redis together.

# --- build stage: install deps with the full toolchain ---
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci                 # cached until package.json changes
COPY . .
RUN npm run build

# --- run stage: copy only what's needed -> tiny final image ---
FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
USER node                  # don't run as root
EXPOSE 3000
CMD ["node", "dist/server.js"]

# Order layers cheap->expensive: deps before code, so a code change
# doesn't re-install node_modules. Add a .dockerignore (node_modules, .git).
# --- build stage ---
FROM golang:1.22-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download        # cached layer
COPY . .
RUN CGO_ENABLED=0 go build -o /app ./cmd/server

# --- run stage: a near-empty image with just the binary ---
FROM gcr.io/distroless/static
COPY --from=build /app /app
EXPOSE 3000
ENTRYPOINT ["/app"]        # final image is a few MB

# docker-compose.yml — the whole stack, one command (`docker compose up`)
# services:
#   app:   { build: ., ports: ["3000:3000"], depends_on: [db, redis] }
#   db:    { image: postgres:16, environment: { POSTGRES_PASSWORD: dev } }
#   redis: { image: redis:7 }

Going further

Multi-stage builds keep the final image tiny (ship the binary/build output, not the compiler). Order layers cheap → expensive so caches survive code changes. Don't run as root, and never bake secrets into the image — pass them as env vars at runtime. docker compose runs your whole stack locally; in production, an orchestrator like Kubernetes or a PaaS (Render, Railway, Fly.io) runs and scales these same images.
MODULE 17

Database migrations: version control for schemas

Your code lives in git — but your database schema changes too. Migrations are small, numbered scripts ("add column", "create index") applied in order. The database keeps a schema_migrations table recording exactly which have run, so every environment converges on the same schema.

The golden rules: migrations run forward in production (write a new migration to undo a mistake), destructive changes get a backup first, and big tables get indexes built CONCURRENTLY so you don't lock production for an hour.

Try: apply all four. V4 drops a column — note the warning ritual. Then roll back and watch the schema and the migrations table stay in sync.

🔧 Go deeper — migration tools & the safe workflow

Nobody runs migrations by hand. A tool applies numbered files in order and records them. Here are the standard tools and the anatomy of one migration.

// Popular tools: Prisma Migrate, Knex, node-pg-migrate, Drizzle.
// Each migration is a numbered file with up (apply) and down (undo).

// migrations/003_add_email_index.js
export const up = (pgm) => {
  pgm.addColumn("users", { email: { type: "text" } });
  pgm.createIndex("users", "email", { unique: true });
};
export const down = (pgm) => {
  pgm.dropIndex("users", "email");
  pgm.dropColumn("users", "email");
};

// Workflow:
//   npx node-pg-migrate up     # apply pending migrations
//   npx node-pg-migrate down   # roll back the last one (dev only)
// Run `up` automatically on deploy, BEFORE the new app version starts.
// Popular tools: golang-migrate, goose, Atlas.
// Migrations are plain .sql files, applied in order.

// migrations/003_add_email_index.up.sql
//   ALTER TABLE users ADD COLUMN email text;
//   CREATE UNIQUE INDEX CONCURRENTLY idx_users_email ON users(email);

// migrations/003_add_email_index.down.sql
//   DROP INDEX idx_users_email;
//   ALTER TABLE users DROP COLUMN email;

// Apply from CI/CD or an init container:
//   migrate -path ./migrations -database "$DATABASE_URL" up

// golang-migrate keeps a schema_migrations table so each file
// runs exactly once, and every environment converges on one schema.

The safe workflow

Commit migrations with the code that needs them — the schema is versioned alongside git. Run them on deploy, before the new app boots. Back up first for destructive changes, and prefer expand-then-contract: add the new column, deploy code that writes both, backfill, then drop the old column in a later migration — so old and new app versions both work during the rollout. Build big indexes CONCURRENTLY to avoid locking writes.

🔧 Go deeper — how to answer a system-design interview

There's no snippet here — system design is about reasoning out loud, not code. Here's the framework interviewers actually score, mapped to the modules you've run.

1 · Clarify & estimate (5 min)

Pin the scope: which features, read-heavy or write-heavy, how many users? Do rough math: "10M users, ~100 reads/sec average, ~10× at peak". These numbers justify every later decision — never skip them.

2 · Draw the happy path

Start with the boring version: client → load balancer → stateless app → database. This is Stage 0–1 of the figure. Say the API shape out loud (POST /urls, GET /{code}).

3 · Find the bottleneck, then add ONE box

Reads dominate? Add a cache (Redis) and read replicas. Slow side-work? A queue + workers. Too much data for one machine? Sharding. Each addition should name the specific pain it removes — exactly the stage-by-stage evolution in FIG. 24.

4 · Name the trade-offs

Show you know the costs: caches go stale (invalidation is hard), replicas have lag, queues make work eventually consistent, sharding complicates joins. Mentioning the downside of your own choice is what separates senior answers.

5 · Talk reliability & scale numbers

Close with the operational layer: health checks & failover, rate limiting, monitoring the p99 latency and queue depth, and how you'd handle 10× growth. Every one of these is a module on this site.

The one-line version: start simple, grow only in response to a named bottleneck, and always say the trade-off. If you can narrate FIG. 24 from one server to spike-proof and explain why at each step, you can pass this interview.
